## 1. Executive Summary

This independent audit conducted a systematic, line-by-line inspection of Phase 6F code and live runtime behavior in a real Chromium browser using Playwright. 

While Phase 6F established a strong foundation with zero autonomous form submission, comprehensive field classification, and evidence provenance tagging, the audit identified **7 specific findings** across pairing authentication, token isolation, candidate data integrity, application tracking semantics, and DOM isolation.

## 3. Detailed Finding Analysis

### Finding SEC-6F-01: Production Exposure of Hardcoded Demo Pairing Code
- **Severity:** HIGH
- **Location:** `api/extension.py`, lines 45–55
- **Reproduction:**
  Send `POST /api/v3/extension/pair` with `{"pairing_code": "demo"}` even when `settings.ENVIRONMENT == "production"`.
- **Observed Behavior:**
  Returns an authenticated session token for `usr_demo_101` (`Alex Rivera`) in production without requiring credentials.
- **Expected Behavior:**
  Demo pairing codes must be strictly blocked in production (`settings.ENVIRONMENT == "production"`). Real pairing must require cryptographically generated pairing codes or verified user credentials.
- **Remediation Plan:**
  Gate demo pairing behind `settings.ENVIRONMENT != "production"`. Enforce user session authentication for pairing code generation.

---

### Finding SEC-6F-02: Absence of Single-Use Expiring Pairing Codes & Rate Limiting
- **Severity:** HIGH
- **Location:** `api/extension.py`
- **Observed Behavior:**
  Pairing codes were static, never expired, and were not tracked in a persistent single-use table. Furthermore, `POST /api/v3/extension/pair` lacked rate limiting, making pairing codes susceptible to brute-force guessing.
- **Expected Behavior:**
  Pairing codes must be:
  1. Cryptographically generated by an authenticated session (`POST /api/v3/extension/pairing-code`).
  2. Stored in SQLite with an expiry timestamp (e.g. 5 minutes).
  3. Single-use (consumed immediately upon pairing).
  4. Rate-limited by IP/client host against brute force.
- **Remediation Plan:**
  Create `ExtensionPairingCodeModel` in `api/models.py`, implement `POST /api/v3/extension/pairing-code` with 5-minute TTL, consume codes upon use, and add rate-limiting.

### Finding SEC-6F-03: Extension Bearer Token Leaked to Content Script Context
- **Severity:** HIGH
- **Location:** `extension/src/background/service-worker.ts`, lines 65–70
- **Observed Behavior:**
  When `content/index.ts` dispatches `chrome.runtime.sendMessage({ type: 'GET_STATE' })`, `service-worker.ts` responds with `currentState`, which included `token: data.resii_token`.
- **Impact:**
  Content scripts do not make direct fetch calls to the RESII API (all network calls go through the background service worker). Storing the secret token in the content script memory space unnecessarily widens the attack surface.
- **Remediation Plan:**
  Redact `token` from state payloads sent to content scripts. Return only `{ isConnected, profile, facts, resumes }`.

---

### Finding SEC-6F-04: Fabricated Candidate Facts Injected for Missing User Data
- **Severity:** CRITICAL (Data Invariant Violation)
- **Location:** `api/extension.py`, lines 145–165
- **Observed Behavior:**
  When a user did not have entries in `CandidateFactsModel`, the API injected hardcoded default facts (`"work_authorization": "Authorized to work in the US"`, `"years_of_experience": "6+ years"`, `"linkedin_url": "https://linkedin.com/in/alex-rivera-dev"`).
- **Impact:**
  Violates the foundational RESII invariant: **"Never fabricate candidate qualifications, employment history, projects, achievements, metrics, certifications, or skills."**
- **Expected Behavior:**
  If a user has not provided candidate facts, they must remain `None` or omitted. The extension classifier must flag these fields as `requiresUserInput: true` with provenance `user_input_required`.
- **Remediation Plan:**
  Remove all hardcoded sample data from `get_candidate_profile`. Only return authenticated candidate facts actually stored in SQLite.

### Finding SEC-6F-05: Application Prematurely Marked as `applied` Without Submission
- **Severity:** MEDIUM
- **Location:** `api/extension.py::track_extension_application`, `review-overlay.ts`
- **Observed Behavior:**
  When the user clicked "Track in RESII", the record was immediately committed with `stage: "applied"`, even though the user had merely filled the form and had not yet submitted the application on the job board.
- **Expected Behavior:**
  Autofilling a form must never label an application as `applied`. It must record it as `draft` or `saved`, and require explicit user confirmation to advance to `applied`.
- **Remediation Plan:**
  Allow the user to select status (`draft` vs `applied`) and default to `draft` when recording during autofill.

---

### Finding SEC-6F-06: LinkedIn in Manifest Matches Without Dedicated Adapter
- **Severity:** MEDIUM
- **Location:** `extension/manifest.json`, `extension/src/content/adapters/`
- **Observed Behavior:**
  `manifest.json` matched `https://*.linkedin.com/jobs/*`, but no `LinkedInAdapter` existed. It fell back to `GenericFormAdapter`, which does not handle LinkedIn Easy Apply modals (`.jobs-easy-apply-modal`).
- **Remediation Plan:**
  Implement `LinkedInAdapter` targeting LinkedIn job postings and Easy Apply modals, and verify it in Playwright browser tests.

---

### Finding SEC-6F-07: Host Page JavaScript Can Inspect Review Overlay DOM
- **Severity:** LOW/MEDIUM
- **Location:** `extension/src/content/review-overlay.ts`
- **Observed Behavior:**
  The review overlay was appended directly to `document.body` as `<div id="resii-review-overlay">`. Malicious or telemetry scripts on the host page could query this element and read rendered candidate information.
- **Remediation Plan:**
  Encapsulate the review overlay inside a **Shadow DOM** (`attachShadow({ mode: 'closed' })`) so host page scripts cannot query inside `#resii-review-overlay` with standard DOM selectors.
